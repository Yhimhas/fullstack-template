# 全栈招新项目模板

这是大一新生二轮考核的个人项目模板。考核时间为一个半月。你需要在自己的仓库里完成前后端项目，具体业务要求和截止时间以另行发放的考核说明为准。

当前模板没有初始化好的工程，也没有业务代码。你会从准备工具开始，逐步做到页面能够向后端发出请求。暂时不认识某个工具，可以先查文档，也可以请 agent 解释。考核结束时，你需要讲清关键实现，并能独立完成小范围修改。

## 先知道代码放在哪里

前端负责浏览器里的页面和交互，代码放在 `frontend/`。后端接收请求、处理业务并返回结果，代码放在 `backend/`。先分别读[前端说明](frontend/README.md)和[后端说明](backend/README.md)，再决定怎样准备环境。

两端都要工程化，也就是用工程文件管理依赖，并提供明确的启动和构建方式。前端不能只交几个独立的 HTML、CSS、JS 文件。后端固定使用 Spring Boot，也要有完整的构建配置，不能只提交零散源码。

仓库里还有两类协作资料。

- [AGENTS.md](AGENTS.md) 约束 agent 的行为。前面的项目补充约定由你填写，后面的必须遵循的规则不能改。
- [.agents/](.agents/README.md) 保存项目技能和会话日志，必须随项目一起提交。

## 把作业放进自己的仓库

Git 仓库保存项目文件和修改历史。clone 是把远程仓库复制到本地；复制模板后，还要确认后续改动会推送到哪里。

你可以从模板创建自己的仓库，也可以 clone 后配置远程地址。无论采用哪种方式，都要确认 `origin` 指向自己的作业仓库。后续 PR 也在自己的仓库内发起，不向模板仓库提交作业。

仓库是否公开、负责人如何取得验收权限，按通知设置。公开前检查内容是否适合发布。私有仓库同样不能存放密码和令牌。

## 第一次先做到能够启动

先读考核说明，确定眼下要完成的任务。随后按两端的说明准备工具。初始化前，检查当前目录和生成位置，两端目录已有的说明、规则和忽略文件需要保留。遇到覆盖提示先弄清用途，避免多生成一层 `frontend/frontend/` 或 `backend/backend/`。

先让前后端分别运行，再接通页面请求。出现错误时，保留实际报错和操作步骤。你可以请 agent 解释错误，再决定下一步怎样处理。

以下操作需要你亲自完成。

- 安装基础工具、配置系统环境，以及初始化前后端工程。官方脚手架和生成器可以使用，选项要自己选择，命令也要自己执行，不能交给 agent 或包办这些操作的一键脚本。
- 至少完成一次项目启动和构建。打开浏览器开发者工具，查看一次实际请求，能说明地址、状态和返回内容。
- 完成首次 Git 提交和推送，并在自己的仓库里完整操作一次 PR。

完成首次练习后，日常开发和检查可以按规则请 agent 协助。你仍要查看改动，对提交结果负责。

## 每个任务怎样保存进展

### 从主分支新建任务分支

分支让你在保留主分支结果的同时，单独完成一项修改。本项目使用一个主分支和短期任务分支，不要求额外维护 `develop` 或 `release`。

下面用 `main` 表示主分支，实际名称以你的仓库默认分支为准。初次导入模板可以直接建立主分支。后续任务从主分支新建分支，验证后通过 PR 合回去。主分支保留能够演示的结果。

分支名使用类型前缀和简短用途，采用小写英文与连字符，不含空格。以下仅为命名示例，不代表考核业务。

```text
feat/form-validation
fix/empty-parameter
docs/start-guide
chore/project-setup
```

`feat/` 表示新功能，`fix/` 表示修复。文档可以用 `docs/`，工程维护可以用 `chore/`。测试和重构也可使用含义明确的相应前缀。

### 提交一项说得清的改动

一次 commit 会把当时选定的改动记入本地历史，推送才会把本地提交发送到远程仓库。每完成一项明确的工作，就检查差异，保存相应进展。

提交标题使用简化的 Conventional Commits 格式。类型用英文，描述可以用中文，范围可以省略。

```text
<type>[(scope)]: <简短描述>

feat(frontend): 增加表单输入校验
fix(backend): 处理空参数
docs: 补充启动说明
test: 增加参数校验测试
chore: 更新会话记录
```

常用类型有 `feat`、`fix` 和 `docs`。重构用 `refactor`，测试用 `test`，日常维护用 `chore`。也可以使用其他含义合适的类型。

一条提交应有一个清楚的目的。差别很大的任务分开提交，标题写出实际变化。不要用“更新”“123”或“完成作业”代替说明，也不要等到考核结束才把全部工作一次性提交。

这里不规定最低提交次数，也不按数量评分。会话日志跟随进展保存，不需要每说一句话就提交一次。

### 通过 PR 合回主分支

PR 是请求把一个分支的修改合入另一个分支。每个任务合回主分支前，都要经过 PR。来源分支和目标分支均应位于你自己的作业仓库。

本项目不提供 PR 模板，你需要自己组织说明。标题写清任务。正文说明修改原因和主要变化，列出实际执行的检查及结果。尚未解决的问题也要写明。

页面有变化时，附实际截图。使用 AI 的重要任务附相关会话日志路径，方便核查讨论和决定。不能用示例截图冒充运行结果，也不能把没执行的检查写成通过。

工作尚未完成时可以先开草稿 PR，完成验证后再准备合并。暂不强制 Issue 编号或 CI；CI 是自动运行检查的流程，本地应做的验证仍要完成。

合并前自己读完整份差异，检查是否误放了文件或敏感信息。日常 PR 可以自查后自行合并，负责人会抽查。如果负责人要求某个 PR 等待 review，就等审核后再处理。自己检查过，不代表其他人已经审核。

合并后先确认代码和会话日志已保留，再决定是否删除任务分支。开始下一项任务前，同步已合并的主分支。切换分支前检查未提交内容，不能靠强制切换丢掉代码或日志。

出现冲突时，先读懂两边改了什么，再处理需要保留的内容。不要擅自覆盖他人的修改，也不要随意强推或改写已共享的历史。

### 请 agent 操作 Git 前单独授权

agent 默认可以查看状态、差异和历史，也可以解释冲突，拟写提交信息及 PR 描述。

之后如需 agent 执行 Git 写操作，要明确授权。提交、推送、创建 PR 和合并 PR，分别逐次确认。一次“全交给你”不能作为长期授权。

## 可以怎样使用 agent

你可以从基础问题问起，也可以讨论技术方案。开始新功能或较大修改前，用自己的话说明本次目标、关键选择和验证办法。暂时说不清时，先请它解释，或做一个小练习，再继续讨论。

讨论清楚后，可以让 agent 在确认范围内写代码、补测试和排查问题，也可以请它安装项目已声明的依赖、运行已有测试和构建。新增依赖、修改构建配置或升级版本前，先了解理由及影响，再明确确认。

不要把考核说明交给 agent 后，只要求它“全部完成”。充分讨论后形成的详细计划可以交给新会话执行，但要把能说明关键决定的讨论线索一起留下。

完整的 agent 行为规则见[AGENTS.md](AGENTS.md)。必须遵循的规则以负责人发布的原版为准，发现差异需要恢复并核查原因，故意绕过按违规处理。文件本身不能阻止修改，执行仍依靠规则和核查。

## 讨论记录也属于项目

agent 在 `.agents/sessions/` 保存会话日志，一次会话一个文件，纯讨论也记录。日志随项目提交，保存前移除密钥、私人信息和考核原文。保存方式和提交时机见[会话记录说明](.agents/sessions/README.md)。

## 开发后更新项目说明

前后端 README 要随实际工程补充。记下采用的版本，提供依赖安装、启动及构建命令。说明必要配置和检查方式，让别人取得仓库后能够照着操作。示例配置只放占位值。

验收时提供仓库和相关 PR，演示实际结果。你需要沿着一次页面请求讲清前后端如何配合，并独立完成要求的小修改。负责人会结合 Git 历史、PR 和会话日志核查过程。
